# Проверка мониторинга — 16 ноября 2026

Основано на двух скриншотах интерфейса и сверке сообщений с текущим исходным кодом v0.4.2.

## Наблюдения

### 1. Ограничение частоты ручных проверок

Интерфейс показывает:

`Please wait at least one minute between manual checks.`

Это не случайный сбой: в `worker/index.ts` ручная проверка возвращает HTTP 429, если с предыдущей проверки этой страницы прошло меньше 60 секунд. Ограничение также описано в настройках безопасности.

**Что улучшить:** показывать остаток времени рядом с кнопкой «Проверить сейчас», блокировать повторный запрос до окончания cooldown и показывать понятное локализованное сообщение. Серверное ограничение оставить.

### 2. Ответ страницы превышает 512 KiB

Для `https://linear.app/pricing` интерфейс показывает ошибку:

`Page exceeds the 512 KB response limit.`

Лимит задан в `worker/monitor.ts`. Он ограничивает размер ответа, который монитор пытается прочитать.

**Что улучшить:** перейти на потоковое чтение с явным лимитом и диагностикой фактического размера/типа ответа. Не загружать неограниченный HTML в память. При превышении лимита показывать статус «Страница слишком большая» и предлагать более конкретный публичный URL или CSS-селектор.

### 3. JavaScript-shell и частичное чтение

Для `https://www.sharrowkin.dev/pricing` сохранено только 27 символов — «Sharrowkin — ИИ-разработчик». Статус «Частичное чтение», цены не извлечены.

Это соответствует текущему ограничению архитектуры: монитор выполняет обычный HTTP-запрос и извлекает доступный HTML-текст; полноценный браузерный JavaScript runtime в Worker не запускается.

**Что улучшить в рамках бюджета €0:**
- проверять Open Graph, Schema.org JSON-LD, microdata и публичные JSON-данные, уже присутствующие в исходном ответе;
- искать встроенные данные гидратации, не исполняя произвольный JavaScript;
- отдельно показывать, что именно извлечено: видимый текст, метаданные, структурированные цены;
- различать пустой app-shell, блокировку сайтом, неподдерживаемый формат и слишком большой ответ.

Не обещать поддержку страниц, содержание которых появляется только после выполнения клиентского JavaScript. Не добавлять платные headless-browser API или сервисы рендеринга.

## Приоритеты для v0.4.3

1. Улучшить UX cooldown ручной проверки.
2. Сделать потоковое чтение ответа с безопасным пределом размера и понятными статусами.
3. Расширить извлечение из доступных HTML/JSON-метаданных и добавить тесты на app-shell.
4. Сохранить текущую безопасность SSRF, ограничения публичных URL и нулевой бюджет.

## Критерии приёмки

- Повторное нажатие «Проверить сейчас» не вызывает серию запросов и показывает время до следующей попытки.
- Большой ответ не приводит к неясной общей ошибке или неконтролируемому потреблению памяти.
- Страница с app-shell получает статус частичного чтения с объяснением причины; пустой shell не выдаётся за полноценный снимок.
- Для каждого нового извлечённого источника данных есть отдельный тест, исключающий ложные цены из обычных чисел и идентификаторов.
